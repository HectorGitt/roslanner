# Full audit — July 2026

Four parallel reviews of the whole codebase: security and tenancy, engine and
solver correctness, database integrity, and the frontend/API surface. Findings
are consolidated here, worst first. Everything marked **confirmed** was traced
through the code; a few are marked **suspected** where the trigger depends on
data or timing not observed directly.

One finding was fixed during the audit (§1). Everything else is open.

---

## 1. Cross-tenant read and write — CRITICAL — **FIXED**

`src/app/api/rosters/[id]/route.ts`

`PATCH` verified that the *roster* belonged to the caller's hospital, then trusted
`edits[].staffId` completely. Any signed-in user could name a staff id belonging
to another hospital; the assignment was written, and the read-back path fetched
that person with `where: { id: { in: extraIds } }` and no hospital filter, so
their name, role and tier came back in the response.

Confirmed by exploit against a live second tenant: hospital A read
`"SECRET Dr. Victim Confidential"` out of hospital B and wrote an assignment row
for them. Publishing then burned that person's `StaffDailyCommitment` slot for a
chosen date, which would have blocked their own hospital from rostering them —
a cross-tenant denial of service on top of the disclosure.

Fixed by validating every edit against the ward's eligible staff, the roster's
day range, and the ward's shift codes, and by scoping the read-back query to the
hospital. Re-running the same exploit now returns 400 and writes nothing. The
edits also run in one transaction, so a bad edit halfway through no longer leaves
a partial save.

**This matters more than it looks:** there are already two real tenants in the
production database, so this was live, not theoretical.

## 2. Nothing checks `User.role` — HIGH

`User.role` is set to `ADMIN` or `MEMBER` and then never read anywhere except to
draw a badge on the settings page. Anyone who joins with the invite code gets
`MEMBER` and can delete a ward and all its history, delete staff, delete tiers,
approve swaps, rewrite every scheduling rule, publish rosters, and read the
invite code to pass on.

Fixing it needs a policy decision about which actions are admin-only, so it isn't
a mechanical change — but as it stands the role column is decoration.

---

## 3. The solver optimises against phantom violations — HIGH

`src/lib/roster/load.ts` returns `chargeLeads: []`, and leads are only computed
*after* the search. So for the whole 2-second hill climb, a ward with
`CHARGE_LEAD_REQUIRED` sees one `CHARGE_LEAD_MISSING` (10,000 cost) for every
staffed shift.

The consequence is not cosmetic: emptying a shift removes that violation, so on a
shift that can't be fully covered, **leaving it empty scores strictly better than
staffing it**. `best.cost > 0` can never be reached either, so every solve burns
the full time budget. This is very likely part of why the demo General Ward — the
only ward with a charge-lead rule — keeps showing last-day gaps that the other
three wards don't.

Cheapest correct fix: when `chargeLeads` is empty, have the check ask "is anyone
on this shift able to lead?", which is the same condition `assignChargeLeads`
uses, so the post-search evaluation still agrees.

---

## 4. Concurrency: several writes are read-then-write with no lock — HIGH

- **Swap approval** re-checks the rules and then applies, with nothing in between
  holding a lock. Two swaps on one roster each check against the *pre-swap* grid,
  both pass, and together they break coverage. Approving the same swap twice
  applies the exchange twice — which swaps it straight back, leaving the record
  saying `APPROVED` and the roster unchanged. Fix: make the status transition
  itself the lock via a conditional `updateMany`, then do the work.
- **`syncRosterCommitments`** deletes then re-creates outside a transaction. Two
  wards publishing at once can leave a published roster with no commitment rows
  for a shared floater, and the "clashes with other wards" count reported to the
  planner can be pure fiction. One-line fix: wrap both in `$transaction`.
- **`saveChargeLeads`** has the same shape; a concurrent read sees zero leads and
  reports every shift as unled.

## 5. Deletes destroy history silently — HIGH

`Staff`, `Ward` and `StaffTier` all delete with no guard, and the cascades run
deep. Deleting one nurse rewrites every published roster she ever appeared on —
the record of who worked which night simply loses rows, and rolling fairness then
recomputes against the altered history. `Staff.active` already exists for exactly
this purpose and isn't used as a barrier.

Deleting a tier is the subtlest: `Staff.tierId` is `SetNull`, so an intern's night
ban evaporates and — because `countsTowardClinicalCoverage` is read off the tier —
**porters start counting as clinical cover**. Meanwhile the tier-scoped coverage
floor is `Cascade`, so the "at least 2 senior staff on every shift" rule is
deleted rather than relaxed. No warning at any point.

Re-optimising a roster also cascades away every `SwapRequest` on it, including
approved ones, taking `reviewedBy` and `reviewedAt` with them — so the audit trail
the swap model exists to keep is destroyed by an ordinary planner action.

## 6. Dangling shift codes switch rules off instead of failing — HIGH

`Assignment.shift` stores a code, not a foreign key — deliberately, so published
rosters survive a ward changing its shifts. But when a code no longer resolves,
every consumer degrades quietly rather than complaining:

- it stops counting as a night, disabling the consecutive-night cap, nights per
  week, the block pattern and night fairness;
- it is skipped by the rest check, as though it were a day off;
- it contributes zero hours to the weekly cap;
- a `CHARGE_LEAD_REQUIRED` rule scoped to a deleted code matches nothing, so it
  enforces nothing while the UI still lists it as enabled.

Nothing anywhere tells the user a roster references a shift that no longer
exists. The fix that converts all of this into one visible problem is an
`UNKNOWN_SHIFT` hard violation in `evaluate()`.

---

## 7. Seed and backfill scripts write straight to production — HIGH

`DATABASE_URL` points at the Cloud SQL instance, and every script picks it up with
no guard, no confirmation and no echo of the target. `node prisma/seed-demo.mjs
--reset-rosters`, run from a dev checkout, deletes every roster in the production
hospital. Add a refusal unless the host is localhost or an explicit override is
set, and print the target before the first write.

Two related problems: `prisma/seed.mjs` creates wards without any
`ShiftDefinition` rows, so a freshly seeded database is rejected by the app
("This ward has no shifts defined") until `backfill-shift-definitions.mjs` is run
— which the README never mentions. And `backfill-commitments.mjs` builds dates
with local-time getters, undoing `normalize-dates.mjs` if run after it.

## 8. Fairness messages can state the opposite of the finding — HIGH

The comparison uses the prior-inclusive rate; the message prints the in-period
count against the combined fair share. Someone flagged as the *most over-worked*
in the pool can be described as being three nights short:

> `Alice: 2 nights at 1 FTE against a fair share of 5.0 counting the last 30 days`

A planner acting on that gives Alice more nights — exactly backwards. Deterministic
whenever a fairness window is set, not an edge case. Report the combined figure the
comparison actually used.

## 9. Swap safety check has a key collision — MEDIUM

`checkSwap` keys violations on type + staff + days. `COVERAGE_SHORTFALL` has no
staff id, so every shortfall on a given day collapses to one key. Going from one
shortfall to three on that day, or from "needs 3, has 2" to "needs 3, has 0",
produces no new-violation entries and the swap is allowed — despite the comment
claiming this catches trading one breach for another. Include the message in the
key and compare counts, not set membership.

---

## 10. Coverage's unique index blocks the legal case and permits the illegal one — HIGH

`@@unique([wardId, shift, roleId, tierId, holidayRule])` omits `daysOfWeek`, so
splitting a role+tier requirement into weekday and weekend rows collides and
returns an unhandled **500** — the day-of-week feature is unusable for exactly the
scope it was built for. Meanwhile the same index enforces nothing when `roleId` or
`tierId` is null, because Postgres treats NULLs as distinct, so duplicates go in
happily and every shortfall on them is reported twice.

Prisma can't express `NULLS NOT DISTINCT`; this needs a raw expression index over
`COALESCE(...)` plus `daysOfWeek`, and dedup in the handler.

## 11. Frontend defects that lose work or mislead — MEDIUM to HIGH

- **Swap cards render "Invalid Date" for every row.** `/api/swaps` returns a raw
  timestamp while the date helper expects `yyyy-mm-dd`, so it builds
  `"…T00:00:00.000ZT00:00:00Z"`. The approver cannot see which days they're
  approving. One-line fix (`slice(0,10)`).
- **Unsaved grid edits vanish** on navigation or reload — no `beforeunload`, and
  the back link doesn't ask.
- **Publishing with unsaved edits** silently discards them and leaves the view
  describing a roster that exists nowhere, because `setStatus` refreshes `data`
  but not `grid`/`dirty`.
- **Renaming a shift code deletes that shift's coverage** silently — the response
  reports orphaned assignments but says nothing about dropped requirements, and
  the ward becomes unrosterable.
- **The coverage tab can't represent two of the four documented scopes** (plain
  headcount, and role+tier together), and because saving does a bulk replace, one
  click permanently deletes rows the page never rendered.
- **Charge leads aren't recomputed after manual edits**, so the "in charge" dot
  can sit on an empty cell and the violation panel argues with a roster the
  planner just fixed.
- **Five pages render calendar dates a day early** in negative-offset timezones by
  formatting UTC-midnight values in local time — dashboard, rosters list, leave
  (both ends), holidays, and the swap picker. Add `timeZone: "UTC"`.
- **`fte` has no UI at all**, so part-time staff can only be created via the API
  despite the solver using it.
- **Every list page swallows its load error** and renders an empty state: the
  dashboard tells a hospital with twelve wards to "set up your first ward"
  whenever the request fails.
- **Two save buttons lock forever on error** (ward Rules, tier eligibility) — no
  `catch`, no `finally`, no message.
- **Cross-ward clash counts are returned by the API and dropped by the UI**, so
  staff silently missing from a roster are never explained.

## 12. Performance — MEDIUM

- `isWeekend`/`dayOfWeek` parse a date string and allocate four `Date` objects per
  call, roughly 1,700 calls per `evaluate()`, and `evaluate()` runs up to 60,000
  times per solve. Precompute day-of-week per day index once. This is likely the
  single biggest cost in the search.
- A dozen other per-call allocations in `evaluate()` (maps and sets rebuilt from
  unchanging input, template-literal keys per staff-day, the `METRICS` array
  rebuilt every call) are all hoistable.
- **There is not a single non-unique index in the database.** Postgres never
  indexes foreign keys automatically. `StaffDailyCommitment.rosterId` is scanned
  on every publish, and `Staff.wardId` on every solve and roster load. One
  migration fixes it.
- Every roster PATCH rebuilds the full solver input and re-evaluates, so editing
  one cell pays the cost of loading an entire roster.

## 13. Smaller confirmed items

- Greedy construction double-counts overlapping coverage requirements, so a ward
  with both a headcount floor and a role requirement gets over-staffed; and
  requirements are iterated in arbitrary order, making shortfalls non-deterministic
  run to run.
- `MAX_HOURS_PER_WEEK` never fires on rosters shorter than seven days.
- `coverageAppliesOn` ignores `daysOfWeek` when `holidayRule` is `ONLY`.
- Cross-ward rest is only checked in one direction (away-then-home, never
  home-then-away).
- `weekendEligible`/`holidayEligible` treat a missing eligibility row differently
  from the rule they mirror, silently dropping whole tiers out of fairness pools.
- `loadPriorStats` computes weekend-ness in local time, contradicting the UTC
  convention everywhere else — history is shifted a day west of UTC.
- Staff appended to a roster after the fact (deactivated but still assigned) get no
  leave, no external shifts and no history, so their approved leave is never
  checked and they look artificially under-loaded.
- `WardRule.tierId` is ignored for `CHARGE_LEAD_REQUIRED`; `shiftCode` is ignored
  for the block pattern and the hours cap. Those scope controls do nothing.
- Duplicate ward rules and duplicate tier pairings are both creatable and both
  double-count their violations.
- `decline` on a swap has no status guard, so an already-applied swap can be
  flipped to `DECLINED`, destroying the accountability trail.
- Invite codes use `Math.random()`, and the join endpoint has no rate limit.
- Rest hours render unformatted: `only 7.333333333333333h rest`.
- `seed-demo.mjs` is not idempotent as claimed: interns and part-timers are picked
  by name order, so re-running reassigns them, and it wipes admin-created
  holidays, ward rules and `canBeLead` choices across the hospital.
- No `active` filter on `GET /api/staff`, so deactivated staff appear in the leave
  dropdown.
- Numerous unvalidated numeric fields (`Number(x)` with no `isFinite` check) turn
  a malformed body into an unhandled 500, and negative values are stored happily —
  `rules` is the worst, with five of them.

## 14. Accessibility

Violations are signalled by a red ring alone, with no text and no `aria-invalid` —
invisible to screen readers and to red-green colour-blind users. Shift identity is
colour plus a one-or-two-letter initial, and two shifts starting with the same
letter are distinguished only by colour. Several affordances are `title`-only
(the charge-lead dot, the float badge, the shortfall warning), which never reaches
touch users. Delete buttons appear on hover with no focus equivalent, so a
keyboard user tabs to an invisible control. The ward tabs aren't marked up as
tabs, several checkboxes have no accessible name, and the grid is 1,200 sequential
tab stops with no roving focus.

---

## What is genuinely sound

Worth recording so it isn't re-litigated. Guard coverage is complete — every one
of the 44 handlers authenticates and returns early. Tenancy scoping is correct in
27 of 28 route files; the roster PATCH was the sole exception. `hospitalId` and
`role` are genuinely not settable by a client at signup (verified against the
Better Auth source, not assumed). The `trustedOrigins` logic is right, and the
route matcher covers every protected page. No secrets are committed, nothing is
logged, and no error response leaks internals. `evaluate()` is pure. Migration
history is verified drift-free against the live database. The consecutive-run
boundary logic, the week-block arithmetic, `restHoursBetween`, and the day −1
external-shift handling were each checked and are correct. `load.ts` batches its
queries properly and deliberately avoids an N+1 on other wards' shift definitions.
